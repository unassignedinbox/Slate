# Entity + Editor System — design

> Design document only. No code. This describes how every entity we add to the game carries its own
> **editor‑side** presence: a user‑chosen **icon/folder**, a user‑designed **inspector**, and an optional
> **dedicated editor window** that opens the entity in isolation (the Unreal asset‑editor idea) — all compiled out
> of shipping builds behind `#ifdef`. It is written to fit the engine that already exists
> (`Engine/Editor/*`, `Engine/DisplayPresentation/IconArt.*`), not a green field.

---

## 0. What already exists (build on this, don't reinvent)

- **`EditorHost`** (`Engine/Editor/EditorHost.h`) — the docked development editor: `ControlPanel`,
  `OutlinerPanel`, `ViewportPanel`, `InspectorPanel`, `NativeConstructPanel`, over an ImGui context.
- **`EditorInstance`** (`Engine/Editor/EditorInstance.h`) — one roster row: stable `InspectorKey`, label,
  `EditorInstanceCategory` (Folder/Geometry/Light/Camera), glyph, tint, visibility/lock/solo, depth for the
  outliner hierarchy.
- **`EditorSheet` → `EditorPropertyGroup` → `EditorProperty`** — the **property‑sheet protocol** the inspector
  draws. Property categories already cover the common controls: **Slider, Switch, AxisVec3, Colour, Select,
  Readout**. This is the "normal UI slider components" path, already built.
- **Bespoke inspector panels** — `SunInspectorPanel`, `MoonInspectorPanel`, `CloudsInspectorPanel`, … — each a
  hand‑drawn UI with its own `EditorSheetAppearance`. This is the "design the UI for itself" path, already built.
- **`IconArt`** (`Engine/DisplayPresentation/IconArt.h`) — a ThorVG **SVG rasteriser** with an LRU cache; icons
  are registered in `IconSymbols.inc` via the `FRONTIER_ICON(Symbol, "file.svg")` X‑macro (generated by
  `ImportApprovedIcons.py`). This is the "user creates SVG icons" mechanism, already built.
- **`ConstructWorld` / `NativeConstructPanel`** — the add‑entity palette; `ConstructEntity(SceneStructure&,
  ConstructRequest{Kind,Name,Position,Size})` places a new entity. This is where "add an entity to the game"
  happens.

The design below is mostly a **registration layer** that ties a new gameplay entity type to those existing pieces
so that adding an entity automatically gives it an outliner row, an icon, an inspector, and (opt‑in) its own
editor window — without editing five panels by hand each time.

---

## 1. Principles

1. **Editor‑side is opt‑in and compiled out of shipping.** Everything an entity declares for the editor lives
   behind a single toggle (`#if FRONTIER_EDITOR`). A shipping build sees only the runtime entity; the icon
   strings, schema tables, and editor‑window factory are gone — zero binary, zero data, zero attack surface.
2. **One declaration per entity, many editor features derived from it.** A new entity type declares its editor
   metadata *once* (icon, folder, category, property schema, optional custom panel, optional dedicated editor).
   The outliner, inspector, construct palette and editor‑window system all read that one declaration.
3. **The editor never owns game state.** As today, panels *borrow* the project's live figures each tick and edit
   in place (`EditorInstance`/`EditorSheet` are filled from the live scene). No bus, no duplicate model, no
   serialization round‑trip to see a change.
4. **Two authoring levels, always both available.** *Cheap*: a declarative schema → an auto‑generated inspector
   from the existing property categories. *Full*: a hand‑drawn custom panel and/or a dedicated editor window when
   the entity deserves it. An entity can start cheap and graduate.

---

## 2. Per‑entity editor declaration (`#ifdef`‑guarded)

When a gameplay entity type is added, it registers an **editor descriptor** next to its runtime definition,
wrapped in `#if FRONTIER_EDITOR … #endif`. Conceptually the descriptor carries:

- **Identity & taxonomy**
  - display name, stable type id;
  - **`EditorInstanceCategory`** (Folder/Geometry/Light/Camera, extensible) — drives default glyph, filter slot,
    and standing‑dot behaviour;
  - **default folder path** in the outliner (e.g. `Gameplay/Enemies`) — where new instances are parented; folders
    already exist as `EditorInstanceCategory::Folder` rows.
- **Icon (user‑chosen SVG)**
  - an `IconSymbol` picked from `IconSymbols.inc`. Authoring a new icon is: drop `my-entity.svg` into the approved
    icon folder, run `ImportApprovedIcons.py` (regenerates the `.inc`), reference the new symbol. `IconArt`
    rasterises and caches it at the panel's logical size and display scale.
  - a per‑instance **tint** override (the outliner already tints rows) and an optional `EditorGlyph` for the small
    14 px row icon vs. the larger content‑browser tile.
- **Inspector schema (declarative, the cheap path)**
  - up to `kMaxEditorSheetGroups` cards, each up to `kMaxEditorGroupProps` properties, each one of the existing
    `EditorPropertyCategory` controls (Slider with range/units/decimals, Switch, AxisVec3, Colour with swatches,
    Select with named options, Readout). The runtime entity exposes get/set hooks the auto‑inspector binds to, so
    a slider move writes the live value on the same tick.
- **Custom inspector (the full path, optional)**
  - a flag + a factory that returns a hand‑drawn panel (the way `SunInspectorPanel` works today) with its own
    `EditorSheetAppearance`. Chosen automatically when present; otherwise the declarative schema is auto‑drawn.
- **Dedicated editor window (optional)** — see §4.
- **Construct palette entry** — whether this type appears in the add‑entity ("Construct") palette, under which
  category, with which icon and default spawn parameters. Extends the existing `ConstructKind`/`ConstructRequest`
  flow so `ConstructEntity` can place it.

A central **editor registry** (editor‑only) collects these descriptors at startup. The outliner enumerates it to
place rows and icons; the construct palette enumerates it for tiles; the inspector looks up the descriptor for the
picked instance's type to decide auto‑schema vs. custom panel; the editor‑window system uses it to spawn windows.

## 3. How the three requested features map

### 3a. "User controls the icon / folder (SVG icons it can create)"
- **Icon:** author an SVG, register it through `ImportApprovedIcons.py` → `IconSymbols.inc`, and name it in the
  entity descriptor. `IconArt` (ThorVG) handles rasterisation, caching, DPI scaling, and a strict policy that
  refuses unapproved SVG features so broken art can't masquerade as approved. Per‑instance tint is already a
  first‑class field.
- **Folder:** the descriptor names a default outliner folder path; folders are ordinary `Folder` rows with a kid
  count badge, and instances can be reparented by drag in the outliner (already supported, minus pinned rows).
  A user can also create empty folders to organise their scene.

### 3b. "The inspector too — design the UI itself, or use normal slider components"
- **Normal components (declarative):** fill the descriptor's schema with `EditorProperty` entries. The
  auto‑inspector renders them with the existing `ControlPanel` controls (slider+type‑in pill, tri‑axis vector,
  colour chip/swatches, select, readout). No drawing code — just data. This is the default and covers most
  entities.
- **Design it yourself (custom panel):** provide a custom inspector panel (like the celestial panels) that draws
  whatever bespoke UI the entity wants — curve editors, previews, gizmo‑linked handles — using the same theme
  tokens and `PixelSpace`/ImGui the other panels use. The registry routes the picked entity to it automatically.
- Both paths edit the project's live figures in place; there is no separate apply step.

### 3c. "It can create an editor — a new window showing the entity isolated with all its properties (Unreal‑style)"
See §4.

## 4. The dedicated Entity Editor window (Unreal asset‑editor analogue)

For entities that warrant it, the descriptor opts into a **dedicated editor window** — a separate top‑level
window (or a floating ImGui viewport) that shows *only that entity*, isolated from the scene, with the full set of
its properties and its own preview. This mirrors Unreal's asset/blueprint editor, and the building blocks already
exist:

- **Isolated preview:** a `ViewportPanel` bound to a *scratch scene* that contains just the one entity on a
  neutral studio backdrop, with its own camera/orbit controls and the same render path (so materials/lighting look
  as they will in‑game). The editor already supports seating an inspector beside Project‑Zero under a distinct
  window title (`InspectorPanel::AssignWindowTitle`, the "SolidArc seat this exact inspector" seam).
- **Full property surface:** the same inspector schema/custom panel from §2/§3b, but given the whole window rather
  than a docked column — room for grouped cards, larger previews (the `EditorSheet` already carries preview
  payloads like sky images, moon bodies, star records, fog/weather previews for exactly this reason), and
  entity‑specific tools.
- **Lifecycle:** opening is triggered from the outliner/inspector (double‑click a row, or an "Open Editor"
  action) → the registry's editor factory for that type spawns the window bound to the entity's `InspectorKey`.
  Multiple entity editors can be open at once; each is an independent panel set over the same borrow‑in‑place feed,
  so edits are live in the main viewport too. Closing writes back nothing special — it was live the whole time.
- **Sub‑editors:** because the window is just panels, a type can add its own (a material sub‑editor, an animation
  timeline, a curve editor) as extra panels inside its editor window, following the same descriptor pattern.

---

## 5. Shipping vs. editor builds

- All of §2–§4 is inside `#if FRONTIER_EDITOR`. A shipping build compiles the runtime entity only; the descriptor
  tables, icon strings, schema, custom panels and window factories are absent.
- The runtime entity type must stand alone without any editor symbol — the editor declaration *references* the
  runtime, never the reverse. This keeps the dependency one‑directional and the shipping build clean.
- Data authored in the editor (placements, property values) is serialised through the normal scene format
  (`SceneCodec`/`SpaceFormat`), so a shipping build loads the same scene without any editor code.

---

## 6. Adding a new entity — the intended workflow (end state)

1. Define the runtime entity (its data + behaviour).
2. In an `#if FRONTIER_EDITOR` block, register its **editor descriptor**: name, category, folder, icon
   (`IconSymbol`), inspector schema *or* a custom panel flag, optional editor‑window flag, and a construct‑palette
   entry.
3. (If a new icon) drop the SVG, run `ImportApprovedIcons.py`.
4. Build with the editor on. The entity now: appears in the Construct palette, places into its folder with its
   icon, shows its inspector when picked, and — if opted in — opens its own isolated editor window. No panel was
   edited by hand.

---

## 7. Open questions to settle before implementation

- **Registry mechanism:** compile‑time X‑macro table (like `IconSymbols.inc`) vs. static‑init self‑registration.
  The X‑macro keeps everything visible in one file and matches the existing icon pattern; self‑registration scales
  better across modules. Recommend starting with the X‑macro to match house style.
- **Schema limits:** current caps are 6 cards × 10 properties. Confirm that's enough for the richest entity, or
  raise `kMaxEditorSheetGroups`/`kMaxEditorGroupProps`.
- **Editor‑window backend:** true OS child windows vs. ImGui multi‑viewport floating windows. Multi‑viewport is
  the least new plumbing given the current ImGui host.
- **Scratch‑scene isolation:** whether the editor window reuses the main render device with a separate scene, or a
  lightweight offscreen target. Offscreen keeps it cheap and matches how the sky/moon previews already bake.
